## 二、技术选型总览

| 层次 | 技术组件 | 选择理由 |
|:---|:---|:---|
| **基座模型** | Qwen2.5-3B-Instruct（首选）或 DeepSeek-R1-Distill-Qwen-1.5B | 中文优异，尺寸适合你的显卡，社区生态成熟 |
| **人格插件** | LoRA（使用PEFT库） | 轻量可插拔，后续可尝试全量微调 |
| **短期记忆** | 上下文滑动窗口（最近30条） | 直接利用模型上下文，无需额外检索 |
| **长期记忆** | RAG + ChromaDB（本地向量库） | 轻量、易集成，适合个人项目 |
| **记忆存储格式** | JSONL + Markdown混合 | JSONL便于结构化检索，Markdown便于人工审阅 |
| **对话归档** | 每次关闭窗口触发归档，写入历史数据库 | 确保跨会话记忆持久化 |
| **前端界面** | Streamlit（Python） | 快速开发、支持滚动加载、日期选择器易实现 |
| **后端推理** | Ollama + 自定义Python API | 统一管理模型，支持GGUF量化 |
| **加速方案** | ROCm + llama.cpp（GGUF） | 发挥你的AMD显卡性能 |

## 四、分阶段实施计划

### 🟢 第一阶段：基础聊天 + 短期记忆（预计2-3天）

**目标**：先让Shelwell能聊起来，具备最近30条的上下文记忆。

| 步骤 | 任务 | 具体操作 |
|:---|:---|:---|
| 1 | 环境搭建 | 安装Ollama，下载 `Qwen2.5-3B-Instruct-GGUF`（Q4_K_M版本） |
| 2 | 验证推理 | 通过Ollama命令行测试模型响应速度与质量 |
| 3 | 创建Streamlit界面 | 搭建纯聊天框，消息按时间倒序排列（最新在底部） |
| 4 | 实现上下文窗口 | 后端维护一个列表，每次请求携带最近30条记录 |
| 5 | 会话状态管理 | 使用Session State存储当前会话的所有消息 |

**验收标准**：可以连续对话30轮以上，Shelwell能准确引用前文内容。

---

### 🟡 第二阶段：长期记忆 + RAG检索（预计3-4天）

**目标**：让Shelwell能"记住"跨会话的信息。

| 步骤 | 任务 | 具体操作 |
|:---|:---|:---|
| 1 | 安装ChromaDB | `pip install chromadb`，初始化本地向量库 |
| 2 | 设计记忆存储格式 | 每条记忆：`{id, timestamp, content, embedding, metadata}` |
| 3 | 实现记忆写入 | 每次对话结束后，将本轮对话按句子/段落切分，向量化后存入ChromaDB |
| 4 | 实现记忆检索 | 用户输入时，先向量化查询，检索Top-3相关记忆 |
| 5 | 实现三级记忆优先级 | ① 上下文30条 → ② RAG检索结果 → ③ 人格生成回复 |
| 6 | 对话归档机制 | 窗口关闭时触发归档，将完整对话写入 `history/YYYY-MM-DD.jsonl` |

**验收标准**：关闭窗口重新打开，Shelwell能回忆起之前的聊天内容（如"你上次说你喜欢喝美式咖啡"）。

---

### 🟠 第三阶段：人格LoRA插件（预计5-7天）

**目标**：为Shelwell注入稳定的个性，而非简单的提示词伪装。

| 步骤 | 任务 | 具体操作 |
|:---|:---|:---|
| 1 | 准备人格数据集 | 收集/生成300-500条体现Shelwell性格的对话（如"温柔知性的朋友"） |
| 2 | 数据格式化 | 转为Alpaca或ShareGPT格式：`{instruction, input, output}` |
| 3 | 安装PEFT + transformers | `pip install peft transformers accelerate` |
| 4 | 配置LoRA参数 | `rank=8, alpha=16, target_modules=["q_proj","v_proj"]` |
| 5 | 训练LoRA | 在Qwen2.5-3B上微调，训练时间约1-2小时（你的显卡可胜任） |
| 6 | 集成到推理流程 | 修改Ollama调用方式，动态加载LoRA权重 |
| 7 | 人格切换测试 | 尝试不同的LoRA插件（如"幽默型"、"严肃型"）对比效果 |

**验收标准**：在不使用任何性格提示词的情况下，Shelwell的回复风格保持一致且鲜明。

---

### 🔵 第四阶段：场景与目标设计（预计2-3天）

**目标**：让对话有"背景"和"方向"，避免空洞。

| 步骤 | 任务 | 具体操作 |
|:---|:---|:---|
| 1 | 设计场景模板 | 如"咖啡厅闲聊"、"深夜心事"、"读书分享"等，每个场景定义：`{背景描述, 语气风格, 推荐话题}` |
| 2 | 场景注入机制 | 用户可选择场景（或系统根据时间/情绪推荐），将场景描述注入系统提示词 |
| 3 | 设计弱目标 | 每个场景附带1-2个"软目标"（如"了解用户最近的心情"），用于引导对话方向，但不强制 |
| 4 | 目标状态追踪 | 在会话状态中记录目标完成度，用于调整回复倾向 |

**验收标准**：在不同场景下，Shelwell的回复风格和关注点有明显差异，且对话不会漫无边际。

---

### 🟣 第五阶段：UI完善与体验优化（预计2-3天）

**目标**：达到类似QQ/微信的聊天体验。

| 步骤 | 任务 | 具体操作 |
|:---|:---|:---|
| 1 | 滚动加载历史 | 使用Streamlit的`st.container` + 虚拟滚动，初始加载最近20条 |
| 2 | 日期跳转功能 | 添加日期选择器，点击后跳转到该日第一条消息 |
| 3 | 消息持久化 | 所有消息存入SQLite（表：`messages`，字段：id, session_id, role, content, timestamp, date） |
| 4 | 自动归档 | 窗口关闭/刷新时调用归档函数，写入长期记忆库 |
| 5 | 响应速度优化 | 使用流式输出（`stream=True`），提升打字机效果体验 |
| 6 | 离线运行验证 | 确保所有功能在没有网络的情况下正常使用 |

**验收标准**：聊天体验流畅，历史记录可追溯，界面简洁无冗余按钮。

## 五、关于「场景」与「目标」的定位分析

你问到这两者是否属于人格的一部分，我的分析是：

| 概念 | 与人格的关系 | 技术归属 |
|:---|:---|:---|
| **场景** | **人格的"舞台"**——同一人格在不同场景下表现不同侧面，但内核一致。 | 属于**上下文增强**，通过动态系统指令注入，不改变模型权重。 |
| **目标** | **人格的"驱动力"**——现实人的性格会驱动行为目标（如"外向者更愿与人建立连接"）。 | 属于**对话策略引导**，可视为人格的动态外显，通过状态机控制回复倾向。 |

**建议实现方式**：
- 场景作为**可选的"氛围包"**，由用户或系统选择，注入到每次请求的上下文中。
- 目标作为**弱引导信号**，在生成时调整temperature或top_p，让回复更倾向于推进目标，但不强制。

## 六、硬件适配与优化建议

针对你的配置：

| 组件 | 优化策略 |
|:---|:---|
| **显卡 (RX 6750 GRE 12G)** | 配置ROCm环境，使用llama.cpp的ROCm后端，推理速度提升3-5倍 |
| **内存 (16GB)** | **强烈建议升级到32GB**（成本约300-400元），否则RAG+模型同时运行会吃力 |
| **模型选择** | 先用Qwen2.5-3B（Q4_K_M），后续可尝试7B的Q3版本 |
| **量化方案** | 统一使用GGUF格式，优先Q4_K_M（平衡速度与质量） |
| **并发处理** | 单用户场景，无需考虑并发，简化架构 |

## 八、技术风险与应对

| 风险 | 应对策略 |
|:---|:---|
| ROCm环境配置失败 | 备选：使用CPU推理（3B模型CPU也能跑）或使用llama.cpp的Vulkan后端 |
| LoRA训练显存不足 | 使用QLoRA（4-bit量化训练），显存需求降至6GB以下 |
| RAG检索效果差 | 优化分块策略（按语义切分而非固定长度），增加重排序（rerank）步骤 |
| 上下文30条不够用 | 可调参数，最终根据模型实际表现调整（Qwen2.5支持128K上下文） |
