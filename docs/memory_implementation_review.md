# Shelwell 记忆系统：分层实现方案与参数建议

> 状态：实现建议稿。本文基于 `ARCHITECTURE.md`、原 `docs/memory_design.md`、现有记忆代码与公开论文/官方文档整理。它将原设计中的目标收敛为可分阶段落地的方案；参数均为首版建议值，需用本地对话集校准。

## 0. 结论摘要

建议采用**分层、证据可追溯、异步巩固、混合检索**的记忆系统：

1. 逐轮原始对话作为情景记忆归档，JSONL 为权威副本；ChromaDB 只做可重建的检索索引。
2. 语义记忆保存从用户陈述中提炼的偏好、稳定事实和带时间的状态；每条事实必须引用来源情景 ID。
3. 在线对话只做归档和检索；评分、提炼、去重、事实更新放后台任务，失败可重试且幂等。
4. 首版用向量检索 + 关键词检索，再用 Reciprocal Rank Fusion（RRF）合并。先不引入知识图谱、自动遗忘和自动物理删除。
5. 首版不按重要性分数丢弃原始对话，也不做自动模糊化。参数先采用下文给出的安全默认值，并通过本地人工标注集调优。

这符合现有项目的单机、ChromaDB、Ollama 和 JSONL 基础；同时避免把研究中的人类遗忘曲线直接当成可用的产品参数。

## 1. 任务分层：从框架到细节

### 1.1 产品目标层

记忆系统只负责三件事：

- 在用户授权的保留策略下保存可追溯的历史证据。
- 在回答前找出相关历史，并控制注入上下文的数量。
- 将重复出现、稳定且有用的信息整理成可更新的事实。

评估目标不是“像人一样忘记”，而是：相关信息能找回、过期事实能被更新、无证据时不会装作记得、用户要求删除时派生内容也一并处理。

### 1.2 系统架构层

按 `ARCHITECTURE.md` 的分层约束实现：

| 层 | 建议职责 | 对应位置 |
|---|---|---|
| L5 接入 | 提供记忆管理界面、审核和删除入口 | `desktop/pages/` |
| L4 编排 | 对话前检索，回复后提交归档任务 | `backend/orchestrator.py` |
| L3 能力 | 记忆 API、提炼、排序、策略和状态机 | `backend/memory/` |
| L2 模型 | 统一嵌入和提炼模型调用 | `backend/llm/` |
| L1 基础设施 | JSONL、ChromaDB、SQLite FTS、配置、任务状态 | `memory/`、`config/` |

L4 不自行实现评分和向量操作；L3 不直接请求 Ollama；索引可从归档重建。持久化后端保持可替换，不在第一版建设独立图数据库或常驻服务集群。

### 1.3 记忆类型层

**情景记忆（episodic）**：一轮完整对话及时间、session、参与者、来源等元信息。它保存“当时说了什么”，是语义事实的证据来源。向量索引保存检索文本或摘要和归档 ID，命中后从权威归档取全文。

**语义记忆（semantic）**：一条可被回答时引用的事实，例如“用户目前在做 Shelwell 项目”。保存事实文本、主体/谓词/对象（可选）、有效时间、置信状态、来源 ID、创建/更新时间、状态和提炼器版本。它回答“当前应该相信什么”。

短期上下文仍由 `context_manager` 管理，不复制进长期库。人格设定和静态知识继续由现有 persona/facts/knowledge 体系提供，不混入用户对话记忆。

### 1.4 数据与一致性层

- **权威记录**：JSONL 或后续 SQLite 数据表保存完整原文；写入带唯一 ID、UTC 时间戳和明确 `session_id`。
- **检索索引**：ChromaDB 保存 embedding、检索文本和 metadata；可清空重建，不视为唯一副本。
- **关键词索引**：首版用 SQLite FTS5 保存同一记录的可检索文本和 ID。若部署环境 SQLite FTS5 不可用，先用 JSONL 倒排/简单匹配作为降级，不新增外部搜索服务。
- **语义事实**：存 JSONL/SQLite 权威表，再同步至独立 Chroma collection；MVP 可以先以 SQLite 为事实表，避免把事实更新、来源引用和删除传播交给向量库 metadata。
- **写入状态**：对话归档、向量索引、关键词索引、提炼状态分开记录。任何派生索引均可重试重建。

JSONL 与 ChromaDB 双写无法原子提交。推荐先提交权威归档，再写入待索引状态；索引失败进入重试队列。批量修复工具按 ID 对账并重建索引。

### 1.5 写入与巩固层

在线路径：生成回复 → 保存用户消息和回复 → 标记索引待处理 → 返回。评分和模型提炼不能阻塞用户回复。

后台巩固：

1. 选择尚未处理的情景记录。
2. 提炼候选事实，必须标出事实来源片段及说话方。
3. 仅把用户陈述作为用户属性/经历的直接证据；AI 回复不能单独确立用户事实。
4. 与现有事实比较；重复则合并来源，更新则结束旧事实有效期并创建新版本，冲突则标记待审核或按明确的时间语义更新。
5. 保存提炼模型、提示模板版本和处理状态，失败可重试，重复运行不重复累加置信度。

优先支持手动“提炼并审核”。自动任务放到第二阶段；避免与在线回复抢占同一个本地模型造成延迟。

### 1.6 检索与回答层

查询时先按 `session_id` 隔离，再并行取语义事实和情景证据候选：

1. 语义向量检索找概念相近事实。
2. 关键词检索找姓名、日期、作品名等精确词。
3. 两路结果用 RRF 合并，避免直接相加量纲不同的余弦分数和 BM25 分数。
4. 语义事实优先注入；有需要时附少量来源情景证据。
5. 按 token 预算截断，并保留来源 ID 供 UI 展示和删除追踪。

用户请求时间变化、纠正或删除时，优先查时间字段、事实状态和来源关系。没有足够证据时应让模型承认不确定，不要仅靠低相似度阈值或“模糊语气”推断记忆可靠性。

### 1.7 生命周期与隐私层

- 删除情景记录时，删除/脱敏归档、所有向量和关键词索引，并重算引用它的语义事实；没有其他来源的事实一并删除或标记不可用。
- “归档/沉睡”与“删除”是不同状态。归档可恢复；删除需作用于所有派生副本。
- 首版只做手动归档和删除，不启用按天数自动降权或物理清理。
- 默认会话键必须明确。普通对话不能以空 `session_id` 做跨会话搜索；管理工具的全局检索需要显式权限路径。

## 2. 参数建议（首版基线）

| 参数 | 建议初值 | 依据与后续校准 |
|---|---:|---|
| 情景记忆原文保留 | 100% 写入（遵循用户删除/保留策略） | 重要性评分暂不作为丢弃原文的开关。若产品决定不永久留存，应先制定保留期与用户可见策略。 |
| 在线写入耗时 | 不调用生成模型；只归档并提交索引任务 | 避免本地模型调用拖慢聊天。索引可异步批处理和重试。 |
| 情景候选数 | dense 20 + lexical 20 | 初始候选池，后续以 Recall@20 和延迟校准；不要把候选池大小当最终注入数。 |
| 语义候选数 | dense 10 + lexical 10 | 之后 RRF 合并并去重。 |
| RRF 平滑常数 `k` | 60 | 常见 RRF 默认量级；它不是相关性阈值。Qdrant 文档说明 RRF 按名次融合，适合分数尺度不同的检索器。小规模数据可比较 10、30、60。 |
| 最终注入数 | 语义最多 5 条、情景最多 2 条；总计最多 7 条 | 控制上下文预算。按 token 数再截断，情景项须有明确检索理由。 |
| 重要性分数 | 0–1，保留两位小数；先记录，不过滤 | 首版暂不设置“4/10 入库”和“7/10 巩固”阈值。收集人工标注后再决定是否启用筛选。 |
| 评分因子权重 | 首版不启用加权总分 | 因子未定义、不同尺度且缺少标注数据。先单独记录“用户明确偏好/承诺/变化/情绪/重复提及”等可解释标签，再拟合权重。 |
| 相似度门槛 | 首版不设全局固定值；取候选后校准 | embedding 模型、索引和 query 类型都会改变距离分布。以标注查询集选阈值或用 RRF 排名加 token 预算。 |
| 语义去重 | 先规范化主体/谓词，再用候选检索 + 审核规则 | 不以 0.85 作为跨模型通用常数。语义近似只召回候选，不能单独证明事实等价。 |
| 自动巩固周期 | 首版手动；第二阶段每日 23:00 可配置 | 23:00 只是运维默认，不是记忆科学参数；按本地时区配置，后台任务需可暂停、重试和查看状态。 |
| 遗忘衰减 | 首版关闭自动衰减 | 先测检索精度、事实更新和删除行为。被检索不等于事实得到确认，不应自动提升置信度。 |
| 复习效应 | 仅在用户再次确认/重复陈述时更新事实置信状态 | 单纯检索命中不得刷新事实真实性。 |
| 冷库阈值 | 首版不设 10 万条或 5GB 硬阈值 | 先测数据库增长、检索延迟和磁盘占用；这些阈值取决于向量维度、硬件及备份策略。 |
| 重试 | 索引/巩固任务最多 5 次指数退避，之后进入待人工处理 | 属于工程运行建议，依据部署运行观测调整；保存错误摘要和任务 ID。 |

### 2.1 关于遗忘曲线

原稿中的 `score_initial * exp(-lambda * days / (score / 10))` 暂不采用。它混合了重要性和强度，且未规定 `lambda`、归一化范围、激活回升和阈值语义。人类记忆研究存在幂律与指数等不同拟合，曲线会受材料、间隔与测试方式影响；因此研究可启发设计，但不能直接给 Shelwell 的 `lambda` 一个普适值。

若后续产品验证需要时间降权，先将它定义为**检索排序上的时间先验**，而非物理遗忘。例如：

```text
recency = exp(-ln(2) * age_days / half_life_days)
rank_score = retrieval_rank_score * (0.8 + 0.2 * recency)
```

起始实验可比较 `half_life_days = 30 / 90 / 180`，并比较“完全不加时间项”的基线；只选能提升本地标注集指标的值。重要事实不应因时间变旧而从有效事实表消失，更新和删除应依赖证据事件。

## 3. 参数校准与验收

先制作 100–200 条脱敏的本地查询样本，覆盖：精确人物/日期查询、偏好回忆、跨轮指代、事实变更、冲突信息、无相关记忆、不同 session 隔离和删除后查询。每条标出正确来源 ID、是否应回答、事实当前状态。

比较向量、关键词、RRF 三种检索方式，以及候选深度 10/20/40 和最终注入数 3/5/7。记录：

- `Recall@k`：相关来源是否进入候选。
- `MRR` 或 `nDCG@k`：正确证据是否靠前。
- 事实更新准确率与删除后残留率。
- 无证据时的错误回忆率（abstention）。
- 检索耗时、嵌入耗时、注入 token 数。

数据少时优先人工看失败案例；不要只看回答流畅度。任何一个阈值改动都留版本号和样本集结果，便于回滚。

## 4. 模块落地建议

```text
backend/memory/
  models.py          # MemoryEvent、SemanticFact、状态与序列化
  archive.py         # 情景归档、ID 查询、删除/脱敏
  indexer.py         # Chroma 与 SQLite FTS5 索引、对账和重建
  extractor.py       # 离线事实提炼，带来源证据
  facts.py           # 事实去重、版本、有效期和来源关系
  retriever.py       # 隔离过滤、候选召回、RRF、token 预算
  jobs.py            # 可重试、幂等的索引/巩固任务
  service.py         # 对外兼容 add_memory/search/get_stats
```

重构时保留 `MemoryRetriever.add_memory/search/get_stats` 兼容入口，逐步把内部实现委托给新模块。更新 `scripts/manage_memory.py`，使其支持新 collection、事实来源、状态和级联删除。迁移时读取旧 JSONL 的 `user`/`assistant` 字段，映射新模型，不要要求用户先清空既有记忆。

建议新增配置（单位写入注释）：

```yaml
memory:
  episodic_collection: "shelwell_episodic"
  semantic_collection: "shelwell_semantic"
  lexical_db: "memory/index/memory_fts.sqlite3"
  episodic_candidates: 20
  semantic_candidates: 10
  final_semantic_top_k: 5
  final_episodic_top_k: 2
  rrf_k: 60
  max_injected_tokens: 1200
  consolidation_mode: "manual" # manual / scheduled
  consolidation_time: "23:00" # 本地时间，HH:MM
  forgetting_enabled: false
```

`max_injected_tokens` 建议先从 1200 token 起步，按实际模型 tokenizer/提示长度和回答质量校准；它是预算，不是要求填满的目标。若无法稳定取得模型 tokenizer，可先按字符数做保守预算并记录实际上下文大小。

## 5. 分阶段实施

### 阶段 A：可靠情景记忆

统一 ID、时间和 session；保留原始归档；让向量索引可重建；搜索结果通过 ID 回查全文；增加隔离、对账、删除传播。暂不评分过滤、事实提炼和遗忘。

### 阶段 B：语义事实与人工审核

增加事实表、来源引用、用户/AI 说话方识别、时间版本和手动提炼审核。先观察误提炼与冲突更新，再开放自动任务。

### 阶段 C：混合检索与评估

加入 SQLite FTS5 和 RRF；构建查询集，比较候选数、融合参数和 token 预算。低成本、精确词查询和语义查询都应有覆盖。

### 阶段 D：运营策略

有足够真实使用数据后，再评估时间降权、自动巩固计划、冷库和删除保留期。只有当这些策略带来可量化收益且不会伤害纠错/删除能力时才启用。

## 6. 文献与技术依据

1. **LongMemEval** 将长期对话记忆拆解为信息提取、多会话推理、时间推理、知识更新和无答案时的拒答能力，并区分索引、检索、读取阶段。可直接作为本系统测试集设计的参考。 [论文](https://arxiv.org/abs/2410.10813)
2. **Zep / Graphiti** 研究强调时间关系和持续更新对跨会话记忆的重要性。其图结构适用于关系密集、实体关系复杂的场景；Shelwell 当前规模不必直接引入图数据库，可先在 SQLite 事实表中落实 `valid_from/valid_to/source_ids`。 [论文](https://arxiv.org/abs/2501.13956)
3. **MemGPT** 提出按层管理上下文与外部记忆，支持“短期上下文与外部长期存储分开”的架构思路；它不意味着每个项目都需要完整的自主代理控制循环。 [论文](https://arxiv.org/abs/2310.08560)
4. **RRF** 适合合并不同尺度的检索排序。Qdrant 官方文档说明，混合搜索可融合 dense 与 sparse/关键词结果，RRF依据名次而非直接相加原始分数。Shelwell 可以用 SQLite FTS5 替代额外搜索服务，再自行实现小型 RRF。 [Qdrant 混合查询文档](https://qdrant.tech/documentation/search/hybrid-queries/)
5. **遗忘曲线研究**指出曲线形状会随任务和实验条件变化，幂律与指数模型均有讨论。因此文献不能直接给出适用于 Shelwell 的固定 `lambda`、睡眠阈值或“人类式”遗忘参数。 [遗忘曲线形式研究](https://www.sciencedirect.com/science/article/pii/S0022249610001100)；[遗忘机制综述](https://pmc.ncbi.nlm.nih.gov/articles/PMC8944258/)

## 7. 与原设计的主要差异

- 原始对话不再由任意评分阈值决定是否保存；留存策略独立、透明。
- 语义事实成为有证据、有时间版本的记录，不仅是向量文档。
- 首版不做细节剥离或按遗忘曲线自动降级，避免制造不准确的“模糊回忆”。
- 评分与相似度阈值从硬编码常数改成待标注校准项；初版优先记录特征，不让未经验证的分数删掉信息。
- 使用本地关键词索引 + Chroma 向量索引 + RRF，保留单机架构，避免早期引入额外服务。
- 将管理脚本、旧 JSONL 迁移、索引重建、级联删除纳入实现范围，避免只完成检索主链路。
