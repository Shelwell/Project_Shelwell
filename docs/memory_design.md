# Shelwell 记忆库设计

> 状态：设计稿，待实现。本文档是记忆系统的唯一设计依据，实现时以本文档为准。
> 前置：`backend/memory_retriever.py` 现状为「日志 + 向量检索」单层结构，本设计将其重构为仿生双层记忆。

---

## 1. 设计目标

现有实现的问题：每轮对话无差别入库、单层混合向量库、只增不减、检索维度单一。本质是「日志 + 相似度检索」，不是记忆。

目标：让记忆系统具备人的几个基本特征——

1. **写入有取舍**：不是每句话都值得记住。
2. **记忆有分层**：情景记忆（发生了什么）与语义记忆（提炼出的事实）分离。
3. **记忆会遗忘**：语义记忆按遗忘曲线衰减，允许沉睡与物理删除（默认只降权）。
4. **记忆会模糊**：细节褪去，核心要点留下，检索呈现「有印象但记不清」的状态。

## 2. 双层仓库

### 2.1 情景记忆（Episodic）

- **内容**：一轮对话的原文（用户消息 + 西尔维娅回复），不做摘要、不切分。
- **载体**：ChromaDB collection `shelwell_episodic` + JSONL 原文归档（真相源）。
- **字段**：
  - `id`：`epi_<uuid12>`
  - `timestamp`：ISO 8601
  - `session_id`：会话隔离键
  - `score`：重要性评分（见第 3 节）
  - `emotion`：情绪标签（预留）
  - `user_msg` / `ai_msg`：原文（JSONL 存全文，ChromaDB 存前 200 字）
- **遗忘**：**不遗忘**。作为真相源永久保留原文。
- **容量边界**：超过阈值（待定，如 10 万条或 5GB）后，最老的低分条目转入冷库（独立 collection，检索时默认不查，可手动唤醒）。

### 2.2 语义记忆（Semantic）

- **内容**：从情景记忆提炼出的结构化事实，例如「用户近期项目压力大，失眠，依赖咖啡」。
- **载体**：ChromaDB collection `shelwell_semantic`。
- **字段**：
  - `id`：`sem_<uuid12>`
  - `fact`：事实陈述（一句话）
  - `subject` / `predicate` / `object`：结构化三元组（用于去重比对，可为空）
  - `score`：重要性评分（初始由来源情景继承，更新时取加权）
  - `strength`：当前记忆强度（遗忘曲线作用对象，见第 5 节）
  - `confidence`：事实置信度（多次从不同情景提炼同一事实则升高）
  - `detail_level`：细节残留度（0-1，越低越模糊，见第 6 节）
  - `source_ids`：来源情景记忆 id 列表
  - `created_at` / `last_activated_at`：创建与最后激活时间
  - `state`：`active` / `dormant`（沉睡，不参与检索）/ `archived`（归档）
- **遗忘**：按遗忘曲线衰减 `strength`，低于阈值转 `dormant`，默认不物理删除。
- **去重**：新增事实前先比对已有条目（同主语+同谓词+近义宾语），命中则更新而非新增。

### 2.3 多用户与群聊模型

Shelwell 接入 QQ 私聊与群聊，同一套记忆系统要服务两种场景，核心矛盾是：**群聊需要连贯的对话上下文，但个人信息不能跨人泄露**。

#### 2.3.1 归属三字段

`MemoryEvent` 在原有字段基础上增加三项，明确「谁在哪个场景说的」：

| 字段 | 含义 | 私聊取值 | 群聊取值 |
|---|---|---|---|
| `speaker_id` | 发言者 QQ 号 | 用户 QQ 号 | 发言人 QQ 号 |
| `channel_type` | 场景类型 | `private` | `group` |
| `channel_id` | 场景标识 | 用户 QQ 号 | 群号 |

`session_id` 保留用于短期上下文隔离，不再作为长期记忆的检索主键。

#### 2.3.2 存储策略：全量归档

**群聊所有消息都归档**，不做过滤。理由：

- 对话连贯性依赖完整上下文，抽掉别人的话会让 A 的发言变得莫名其妙
- 定期提炼需要完整素材，事后补不回来
- 只记「被响应的」会漏掉大量有价值信息

群聊消息的 `speaker_id` 标记发言人，`channel_id` 标记群号。这样一条记忆同时携带「在哪个群」和「谁说的」两个维度。

#### 2.3.3 检索规则：视角隔离

检索条件按场景区分，实现非对称的隐私边界：

| 场景 | 查询条件 | 效果 |
|---|---|---|
| **A 私聊** | `speaker_id = A` | 能看到 A 在私聊和所有群里的发言，看不到任何其他人说的 |
| **群 G 内** | `channel_id = G` | 能看到群 G 里的全部对话（所有人），用于理解上下文 |

由此自然形成两条规则：

- **群聊 → 私聊：允许**。A 在群里说的话，`speaker_id` 是 A，私聊时查得到，属于「自己说过的话自己记得」。
- **私聊 → 群聊：禁止**。A 的私聊记录 `channel_id` 是 A 的 QQ 号，群聊查 `channel_id = G` 匹配不到，天然隔离。

群聊里能看到所有人的发言，但**这些发言在提炼为语义事实时，只归到发言者个人名下**，不会变成别人的信息。A 说「我下周去成都」，这条事实的 owner 是 A，B 问起成都时不会命中。

#### 2.3.4 触发策略

群聊消息量大，不能每条都回复。触发条件（满足任一即响应）：

- **@ 机器人**
- **关键词命中**：`西尔维娅`、`西儿`、`小西`、`维娅`（可在 `app_config.yaml` 的 `qq_bot.trigger_keywords` 配置，后续按需追加）

未触发的消息仍全量归档，只是不调用模型回复。归档是后台行为，不影响群聊体验。

关键词匹配规则：
- 中文词按子串匹配（「希」能命中「希望」这类误伤，需配置时权衡，或用词边界控制）
- 英文词忽略大小写
- 匹配到即触发，不做上下文判断

#### 2.3.5 语义提炼的归属边界

定期提炼时，从情景记忆提取事实，归属规则：

- A 的发言 → 提取的事实归 A（`owner_id = A`）
- 群聊中 B 的发言 → 即使 A 在场，事实也归 B，不进 A 的语义记忆
- 群体共识类事实（如「这个群在筹备聚会」）→ 归群层（`owner_type = group`, `owner_id = G`），群成员都能查到

群层语义记忆是第二阶段的事，首版只做个人层。

#### 2.3.6 对现有代码的影响

| 模块 | 改动 |
|---|---|
| `models.py` | `MemoryEvent` 加 `speaker_id` / `channel_type` / `channel_id` 三字段，`from_dict` 兼容旧数据（从 `session_id` 解析） |
| `service.py` | `search` 的 `where` 条件从 `session_id` 改为 `speaker_id` 或 `channel_id` |
| `indexer.py` | ChromaDB metadata 加三字段，供 `where` 过滤 |
| `qq_bot/main.py` | 群消息解析 `sender.user_id` / `sender.card`，判断触发后决定是否回复；`session_id` 与记忆归属分离 |
| `context_manager.py` | 检索调用时传入当前场景的 `speaker_id` / `channel_type` / `channel_id` |

**向后兼容**：旧数据只有 `session_id`，迁移时按 `qq:{uid}` → `speaker_id=uid, channel_type=private, channel_id=uid` 解析；`qqg:{gid}:{uid}` → `speaker_id=uid, channel_type=group, channel_id=gid`。

## 3. 重要性评分

### 3.1 设计原则

纯信息论（Shannon `-log P`）只衡量字面稀缺度，会漏掉「朴素但重要」的陈述（如「我把猫送人了」，每个字都常见，但必须记住）。因此采用**多因子加权**，信息量只占其中一项。

### 3.2 评分区间与阈值（待定，需文献支撑）

- 评分范围：**0-10**（整数或一位小数）
- **入库阈值**：默认 **4.0**，低于此值丢弃，不入情景记忆
- **巩固阈值**：默认 **7.0**，高于此值的情景记忆优先参与提炼

> 阈值需在实现后基于真实对话样本校准，初值仅供参考。

### 3.3 因子构成（待文献确定权重）

| 因子 | 含义 | 计算方式（候选） |
|---|---|---|
| 信息量 | 文本的非冗余度 | `-log P` 近似（基于词频或 TF-IDF） |
| 情绪强度 | 情绪词、感叹、极端表达 | 情绪词典匹配 / 模型判断 |
| 事实密度 | 含具体人/时/地/事件/偏好的程度 | 实体抽取 + 陈述句模式匹配 |
| 自我指涉 | 是否涉及用户、西尔维娅、两人关系 | 关键词 + 代词指向分析 |

**权重 `w1..w4` 与各因子的具体算法，待查阅文献后确定并回填本节。**

## 4. 写入流程
一轮对话（user + assistant）↓[1] 计算重要性评分 score↓score < 入库阈值 ? ──是──→ 丢弃，不入库（仍可在短期上下文里，但不进长期记忆）│否↓[2] 写入情景记忆├─ JSONL 追加原文（真相源）└─ ChromaDB 写入向量 + metadata（含 score / timestamp / session_id）text复制下载
**要点**：
- 写入是同步的，评分计算必须轻量（规则优先，模型判断作为兜底）。
- 评分失败时降级处理：默认按中等分（5.0）入库，避免丢数据。
- JSONL 与 ChromaDB 双写，任一失败不影响另一条，但需记录不一致日志（后续补偿）。

## 5. 巩固与提炼（情景 → 语义）

语义记忆不是凭空产生的，从情景记忆中提炼而来。

### 5.1 触发时机

管理 UI 中提供两种模式，可切换：

| 模式 | 触发条件 | 说明 |
|---|---|---|
| **手动提炼** | 用户点按钮 | 立即扫描未提炼的情景记忆，跑一轮提炼 |
| **自动提炼** | 每天固定时间（默认 23:00）/ AI 休眠时 | 后台任务，静默执行 |

> 「AI 休眠」功能后续实现，届时自动提炼挂到休眠流程上。

### 5.2 提炼流程
选取待提炼情景记忆（score ≥ 巩固阈值 且 未提炼过）↓批量送入主模型，提取结构化事实↓对每条事实：├─ 与已有语义记忆比对（subject+predicate+object 或语义相似度）├─ 命中 → 更新：合并 source_ids、score 取加权、confidence 提升、刷新 last_activated_at└─ 未命中 → 新增语义记忆条目text复制下载
### 5.3 去重规则

- **强匹配**：三元组完全一致 → 必定是同一事实，更新
- **弱匹配**：语义相似度 ≥ 阈值（如 0.85）且主语一致 → 视为同一事实，合并
- **冲突**：同一主语+谓词但宾语矛盾（如「用户喜欢咖啡」vs「用户讨厌咖啡」）→ 不覆盖，保留两条，靠时间戳和 confidence 区分，或标记为「状态变更」新增条目

## 6. 检索流程
query↓[1] 先查语义记忆├─ 向量相似度 × strength 加权排序├─ 过滤 state == active└─ 取 Top-K↓[2] 命中数不足 或 最高相似度低于阈值 ?├─ 是 → 回退查情景记忆（相似度 × 时间权重）└─ 否 → 只用语义结果↓[3] 合并结果（语义优先，情景补充）↓[4] 按 detail_level 选择注入模板（见第 7 节）↓[5] 更新被命中记忆的 last_activated_at 与 strength（激活 = 复习）text复制下载
**排序公式**：
- 语义记忆：`rank = similarity * (0.5 + 0.5 * strength_normalized)`
- 情景记忆：`rank = similarity * time_decay(timestamp)`

**回退条件**：语义命中 < `top_k` 且情景库非空，或语义最高相似度 < 0.5。

## 7. 模糊记忆

模拟「有印象但细节想不起」的状态，通过语义记忆的 `detail_level` 实现，不新增仓库。

### 7.1 语义化降级

语义记忆长期未激活、或 strength 衰减到中间区间时，触发**细节剥离**：

- 保留：核心要点（主语+谓词+宾语的主干）
- 剥离：时间、地点、具体名称等细节（这些细节仍在情景记忆中可查）
- `detail_level` 下调

### 7.2 检索呈现三态

| detail_level | 状态 | 注入方式 |
|---|---|---|
| ≥ 0.7 | 清晰 | 直接陈述事实 |
| 0.3 ~ 0.7 | 模糊 | 加限定语，如「大概记得……」「好像提过……」 |
| < 0.3 | 极模糊 | 只给核心要点 + 不确定标记，让模型自己决定是否追问 |

### 7.3 与遗忘的关系

遗忘流程分两段：
1. **语义化**（模糊化）：strength 下降到中间区间，先剥离细节，`detail_level` 降低
2. **沉睡**：strength 继续下降至阈值以下，`state` 转 `dormant`，不参与检索

模糊化是沉睡之前的中间态，不是删除。

## 8. 遗忘机制

### 8.1 遗忘曲线

参考 Ebbinghaus：`R = e^(-t/S)`，S 为记忆强度。

实际采用：
strength_new = score_initial * exp(-lambda * days_since_last_activation / (score / 10))text复制下载
- `score` 越高，衰减越慢
- 每次被检索命中（激活），`last_activated_at` 刷新，strength 回升，且衰减速率降低（复习效应）

### 8.2 状态流转
active（正常参与检索）↓ strength 降至中间区间（语义化降级，detail_level 下降）↓ strength 低于沉睡阈值dormant（不参与检索，不删除）↓ 手动或长期未激活archived（归档到冷库，可恢复）text复制下载
### 8.3 删除策略

- **默认只降权不删除**（当前阶段）
- 管理 UI 中提供「允许物理删除」开关（后续实现）
- 物理删除仅作用于 `archived` 状态且超过保留期的条目

### 8.4 情景记忆的遗忘

情景记忆**不遗忘**（真相源），仅有容量边界：超过阈值后最老的低分条目转冷库，不删除。

## 9. 模块划分（落地时）

| 模块 | 职责 |
|---|---|
| `backend/memory/scorer.py` | 重要性评分（多因子） |
| `backend/memory/episodic.py` | 情景记忆读写、JSONL 归档、冷库迁移 |
| `backend/memory/semantic.py` | 语义记忆读写、去重、强度更新 |
| `backend/memory/consolidator.py` | 巩固提炼（情景→语义），手动/自动触发 |
| `backend/memory/retriever.py` | 统一检索入口，双层查询 + 回退 + 排序 |
| `backend/memory/forgetting.py` | 遗忘曲线计算、语义化降级、状态流转 |

现有 `backend/memory_retriever.py` 重构为上述模块的聚合入口，对外接口保持 `add_memory` / `search` 兼容，内部替换实现。
